# 视觉重设计参考研究

检查日期：2026-10-17（Asia/Shanghai）。范围：个人主页与全部非 iCube 产品、支持、隐私、更新及语言版本。iCube 不纳入设计或迁移。

这份研究服务于一个持续增加产品的独立 Apple 开发者网站。它不是竞品流量或转化率研究；没有用户访谈、分析后台或 A/B 测试数据。下文明确区分「观察事实」「设计推断」与「本项目建议」。所有案例内容来自官方站点，未复制其营销文案。价格、版本与产品数量只是当日页面状态，不作为本项目的内容。

## 1. 结论先行

建议采用「个人作品集 + 可增长的应用目录 + 一致的产品与文档模板」：主页快速回答“谁做的、有哪些、哪个适合我”；产品页回答“能解决什么、真实界面怎样、适用于哪些设备、如何获取”；支持页回答“我遇到问题该怎么做”。三类任务共享排版、导航、交互和内容结构，视觉密度各有区别。

视觉方向建议为温和的浅色无衬线系统，产品图标、真实截图和少量强调色承担个性。保留作者身份与个人经历，不扩充企业式价值口号。没有证据支持通过统一增加大字、大留白、动效或复杂卡片就能提升效果；这些只能作为待验证的设计选择。

研究最强的组合是：Sindre Sorhus 的目录结构，Things 的任务叙事节奏，Panic 的作者品牌与产品品牌分层，Tapbots 的小团队人格，Soulver 的具体使用示例，Bear 的功能/付费/语言边界。

## 2. 研究方法与证据边界

- 访问六组官方案例：Panic/Nova、Sindre Sorhus/Dato、Things、Tapbots/Ivory、Soulver、Bear。
- 文本与结构：通过官方页面逐页读取导航、章节、截图描述、支持入口与语言入口。
- 实际视觉：在浏览器观察了 Sindre 应用目录、Panic 首页、Nova 首屏、Things 首屏和后续截图章节。可以据此描述这些页面的视觉层级与留白；没有对所有页面做完整尺寸矩阵检查。
- Tapbots 浏览器连接失败；后续浏览器新建受到执行环境限制。Tapbots、Soulver、Bear 的结论以官方页面内容结构为主，不宣称已完成其字体、颜色、间距或响应式视觉核验。
- 没有检验参考站点的实际转化率、无障碍合规程度或加载指标；看起来简洁不代表已满足规范。
- 未确认竞品使用的精确字体文件或许可证。视觉上属于无衬线或衬线的描述不等同于确认字体家族名称。

## 3. 六组一手参考

### A. Sindre Sorhus：目录扩张最直接的参考

**观察事实。** 应用目录区分 Featured 与 More Apps，提供平台、价格类型等分类入口。卡片呈现图标、名称、用途和状态，页尾另有 FAQ、旧版本、归档应用等入口。当日桌面视图以深色背景、无衬线层级和两列紧凑卡片组织产品；没有给每个产品都分配大型截图舞台。[应用目录](https://sindresorhus.com/apps)

Dato 产品页将名称、用途、获取方式、平台信息放在前部，随后提供截图、功能介绍、Tips、FAQ、脚本和支持入口。[Dato](https://sindresorhus.com/dato)

**设计推断。** 目录可持续增长，依赖的是固定的元信息契约和精选层级，不是卡片数量恰好适配某个屏幕。统一目录不妨碍产品页承担更多解释工作。

**适合借鉴。** 首页至多 1–2 个重点产品，其余产品采用紧凑目录；每项都有一致的一句话用途、平台和状态。未来归档产品仍有稳定 URL 和明确维护状态。

**不适合直接照搬。** 当前六个产品不需要一整排十余个筛选项、随机应用入口或很深的分类页。先保留分类数据，等产品达到约 12–15 个、且用户确实需要筛选时再呈现筛选 UI；这个数量是项目设计假设，不是普适阈值。深色渐变也是其品牌选择，不是目录扩张的必要条件。

### B. Panic / Nova：共享作者背书，允许产品有自己的性格

**观察事实。** Panic 首页将软件、游戏、硬件分组，底部支持按产品获取帮助，并有日文入口；当日首屏使用大型游戏宣传图。Nova 作为产品站保留 Panic 回链，导航突出帮助、扩展、文档和购买；正文区分新版本内容和日常功能，下载附近明确列出试用、系统要求与更新记录。[Panic](https://panic.com/) · [Nova](https://nova.app/)

实际观察的 Nova 首屏采用深色背景、醒目的品牌标记、衬线副标题、真实编辑器界面和高对比行动按钮，说明「一个站必须全程只使用一种字形或一种截图布局」并非必要。

**设计推断。** 家族一致性应该体现在入口、信息位置和基本交互，不必抹平产品特征。独立产品的强调色和截图构图可以变化，共享导航和内容规则仍能建立关系。

**适合借鉴。** 每个产品页保留清楚的“Jamin / 所有应用”返回路径；主行动附近展示可验证的平台、系统要求与分发方式；功能介绍可以直达帮助文档。

**不适合直接照搬。** 全屏宣传接管、多个沉浸式营销段落、各产品自成一套导航与技术实现，会增加本项目的维护成本，也可能推迟用户看到应用目录的时间。

### C. Things：先说明用途，再逐层展开

**观察事实。** 主导航很短；首屏是大图标、产品名、简短用途和视频入口，随后有界面展示、功能入口、多设备下载与要求。支持页按入门、基础、同步、进阶、技巧和排障组织，并保留联系入口。[Things](https://culturedcode.com/things/) · [Things Support](https://culturedcode.com/things/support/)

实际桌面观察看到浅灰底、清楚的无衬线层级、较多留白，以及后续放大的界面细节。**大图标首屏本身并不是设计错误**；它能否工作，取决于品牌识别、后续产品证据和整体页面任务。本项目应重点解决同等巨型陈列与截图证据不一致，而不是机械禁止大图标。

**设计推断。** 界面展示应有节奏：先给清晰整体认识，再解释关键任务，最后补足平台与支持信息。一个功能丰富的旗舰产品可以有较长叙事，小工具则应缩短。

**适合借鉴。** 产品页只挑 2–3 个最有解释力的真实任务，配合对应截图；支持按用户问题组织，不按代码模块组织。

**不适合直接照搬。** 成熟单品的长篇媒体评价和大面积视频入口，不适合每个小产品都复制。没有已核验的评价、奖项或下载量时，不应创建装饰性的社会证明模块。

### D. Tapbots / Ivory：小团队人格与使用上下文

**观察事实。** Tapbots 首页以产品图标、名称、简短定位、平台/指南入口组织作品，并介绍真实团队。Ivory 产品页提供多设备界面、系统要求、帮助入口，再展开用户需要理解的使用背景与功能。[Tapbots](https://tapbots.com/) · [Ivory](https://tapbots.com/ivory/)

**设计推断。** 独立作者身份本身是有价值的信息，不需要伪装成大公司的团队规模。对门槛较高的产品，解释使用情境比堆砌功能名更有帮助。

**适合借鉴。** 首页保留简短作者介绍、真实经历和联系方式；产品页中的内容长度依据理解难度变化。链接文案应具体到“设置首次提醒”或“导入数据”，而非反复“了解更多”。

**不适合直接照搬。** 不为视觉改版额外创建机器人角色世界、复杂插画或品牌音效。现有六款产品的图标已经有个性，统一网站不需要重造一套角色体系。

### E. Soulver：用具体例子证明价值

**观察事实。** 首页将用途与获取方式放在前部，随后以旅行、费用、变量等具体示例展示产品如何工作，并按记事、计算、应用等主题组织较深内容，复杂主题可跳到文档。[Soulver](https://soulver.app/)

**设计推断。** 对工具类应用，访客理解一个具体任务，往往比阅读抽象形容词更容易判断是否适合自己。这是信息设计假设，不是已测得的转化结论。

**适合借鉴。** PriceBird、Rouse 等页面应展示“输入/设置 → 结果”的一段真实工作流；文案直接描述结果。演示数据必须注明或明显属于示例，不能伪装真实市场价格、个人财务或用户使用记录。

**不适合直接照搬。** 不把所有功能都塞成复杂交互 demo，不在静态营销页面重建整个应用。多数功能用可放大截图、短标注和结构化文案即可解释。

### F. Bear：保留产品温度，同时明确内容边界

**观察事实。** Bear 官方页按功能主题组织截图和说明，付费能力带 PRO 标记，提供定价、帮助、隐私和中文版入口。中文站保留相近的信息骨架，但部分外部入口明确标为英文内容；帮助页单独承载入门和操作主题。[Bear](https://bear.app/) · [中文版](https://bear.app/zh/) · [帮助](https://bear.app/faq/)

**设计推断。** 多语言复用应是结构共享、内容独立：不能只换导航标签，也不能为了外观对称虚构完整翻译。功能与付费边界属于产品理解的一部分，应该在相邻位置说清。

**适合借鉴。** 产品状态、免费/付费内容、隐私说明各自有明确字段；语言切换尽量留在同一产品和页面类型，无对应语言时明示实际目标语言。

**不适合直接照搬。** 不为每个应用套用复杂 Free/Pro 对比表；只有实际商业模式需要时才展示。插画、社群和 newsletter 也必须有真实维护能力才加入。

## 4. 三条视觉方向的取舍

以下均为本项目设计判断，尚无用户测试结果。

| 方向 | 优点 | 成本与风险 | 结论 |
| --- | --- | --- | --- |
| 温和的原生工具作品集 | 系统无衬线、明亮中性色、真实截图、紧凑目录；适合 Apple 产品和多语言 | 需要精确控制截图、留白与文案，否则容易普通 | 推荐为基础方向 |
| 编辑部式个人作品集 | 小量衬线展示标题、无衬线正文、作者感强 | 中英日字形协调和标题长度更难；容易延续旧站的书刊气质 | 可作为首页标题的有限变体 |
| 多彩产品展厅 | 每个产品大色块、强舞台、动效 | 产品增长后页面变长，资产与动效维护成本高；不利于文档一致性 | 仅借用一个精选区域，不作为整站骨架 |

推荐统一的不是“每页看起来相同”，而是阅读逻辑和操作预期。主页可以更有编辑感；产品页可以有自己的强调色；支持与隐私页应更安静。

## 5. 字体与排版决策

### 建议基线

- 主字体采用系统无衬线栈，标题和正文使用同一个基础家族；用字重、字号、行高和空间建立层级。
- 不把 SF Pro 字体文件打包进网站。通过系统栈使用设备现有字体；若决定加入其他品牌字体，先核对网页嵌入许可证和所需语言覆盖。
- 中文和日文按页面语言设置回退，不把某一套中文字体强行用于所有 CJK 文本。设计与验收必须覆盖 macOS、iOS 以及至少一个非 Apple 环境，因为 system-ui 的最终字形不是固定的。
- 首页展示标题可试 52–64px 桌面、36–44px 手机；产品页 44–56px / 32–40px；正文 16–18px；辅助信息 13–14px 作为起点。全部用相对单位与响应式区间实现，最后以真实中英日文案验证，不把这些数值当规范。
- 英文正文行高约 1.55–1.65；中文/日文约 1.7–1.8。标题不沿用正文行高。长文采用较窄阅读列，英文约 60–75 字符、中文约 28–38 字为初始校准范围。
- 标题采用自然换行，不对每种语言共用硬编码 `<br>`；不要为齐整固定标题容器高度。小字号不使用大幅负字距；CJK 默认不要套英文标题的负字距。
- 平台和状态标签避免过密的大写字母；正文链接保留下划线或等效非颜色线索。数字、版本、日期可在需要对齐时使用等宽数字，不把整段正文改成等宽字体。

### 性能约束

web.dev 说明字体加载与首次文字绘制会竞争，`font-display` 和 preload 可控制行为。**建议**优先系统字体；若使用品牌 webfont，只加载实际使用的字重与字集、提供可靠回退、避免为所有语言预载大字库，并测试替换前后的布局变化。`font-display: swap` 能显示回退文字，但不是自动保证没有位移。[字体加载与渲染](https://web.dev/articles/optimize-webfont-loading)

## 6. 截图与视觉素材的重用方式

以下为本项目建议。

1. 保存原始截图与网页派生资源，避免只保留压缩后成品。每个素材记录产品、平台、语言、应用版本、拍摄日期、用途与来源。
2. 定义三种稳定的媒体容器：单个桌面窗口、手机/平板组合、局部操作细节。不同产品可选不同组合，不必全部套相同设备框。
3. 首页精选展示一个能讲清核心用途的画面；普通目录不放微小难读截图。详情页用较大的真实截图解释，手机上不要把多个设备继续缩成一排。
4. 截图和装饰背景分开：窗口保留正确纵横比，背景色由产品 token 控制。统一外部圆角、阴影与画面呼吸空间，不改造产品内部 UI。
5. UI 文本必须在实际显示尺寸下可理解；需要展示完整画面时，旁边给短的文字解释。支持放大查看时保证键盘关闭、可见关闭按钮与焦点返回。
6. 图片缺失时使用真实图标和简短功能说明，或明确标注的概念示意；不能把 AI 生成界面或 HTML 重绘图误称为真实截图。
7. 社交分享图使用独立构图：产品名、图标、一句用途和可识别截图，不直接截整张网页。多语言版本至少保证标题与描述对应，不让文字溢出。

web.dev 区分了两种响应式图片需求：`srcset`/`sizes` 用于让浏览器选择合适资源，`picture` 用于需要明确控制画幅或格式的情况。**建议**桌面/手机不同构图仅在确实提升可读性时使用 art direction，避免只是把同一图无差别放大缩小。[响应式图片](https://web.dev/learn/images/responsive-images)

LCP 首图不能懒加载，可给予合适的获取优先级；首屏以下素材可以延后。图片应有尺寸或纵横比预留空间，字体替换和延迟图片都需要纳入布局稳定性检查。[LCP 优化](https://web.dev/articles/optimize-lcp) · [CLS 优化](https://web.dev/articles/optimize-cls)

## 7. 可重用信息架构与组件

### 四层复用

| 层级 | 共享什么 | 允许变化什么 |
| --- | --- | --- |
| 设计基础 | 颜色语义、字体、间距、圆角、阴影、焦点与动效 | 产品强调色，页面语言的排版微调 |
| 原子与组合组件 | 按钮、链接、标签、导航、目录项、截图框、FAQ、提示、页脚 | 文案、图标、数量、状态，不复制 CSS |
| 页面模板 | 首页、产品、支持/文档、隐私、更新、404 | 可选章节、产品故事顺序、媒体构图 |
| 内容与资产 | 产品信息契约、语言键、资源命名与尺寸规则 | 每款产品的事实、截图、支持内容 |

### 内容契约应覆盖的字段

产品标识与稳定路径、显示名、一句话用途、短介绍、图标、强调色、支持平台、产品状态、获取方式、主要/次要 CTA、最低系统要求、截图集合、核心任务、功能、隐私摘要、支持/隐私/更新链接、可用语言、社交分享图、精选排序。价格与版本如无法持续更新，可链接至权威商店页，不把容易过期的数字写死在共享模板。

一个值只应有一个内容来源。语言内容与布局分开，但不要把整个页面塞进无法审阅的大字符串；富文本只开放实际需要的结构。

### 三种页面密度

- **首页/目录**：简短身份介绍 → 一个精选区域 → 全部应用 → 简短作者信息 → 支持与联系。精选产品仍保留在全部应用中，避免用户误以为目录不完整。
- **产品页**：名称/一句话用途/平台/获取 → 核心截图 → 2–3 个任务 → 必要功能与隐私边界 → FAQ/支持 → 最后获取入口。小工具可以跳过缺乏内容的章节；复杂产品可扩展。
- **文档页**：面包屑、清晰标题、必要的更新时间、短引导、目录/正文、相关帮助、联系入口。隐私页重视长文阅读，更新页重视日期和版本，不共用产品页的巨大首屏。

### 不应随产品复制的东西

每页独立字体导入、重复导航脚本、单页专属通用按钮 CSS、同一隐私段落的多份手工拷贝、硬编码的语言列表、多个相互偏离的页脚。真正有产品差异的隐私与支持事实必须保留差异，不能为了模板统一改写成错误的共同承诺。

### 与现有技术约束的关系

过去的项目记录倾向于构建时生成静态 HTML，并将内容与模板分离；这是历史基线，具体当前脚本和目录仍须以本轮仓库检查为准。设计复用不要求运行时应用框架：共享 token、模板、内容清单和静态输出即可实现。iCube 路径和它依赖的资产应作为显式排除边界，避免全局选择器或共享文件改动间接影响它。

## 8. 导航、多语言与状态细节

以下为本项目建议。

- 顶层导航保持少量稳定入口：应用、关于、支持/联系、语言。个人首页不需要把六个产品全塞进主导航；产品局部导航只出现有内容的章节。
- 产品页任何入口都能回到所有应用；支持页保留当前产品上下文，避免用户在求助时丢失产品名。
- 手机菜单用真实 button，开关状态有名称，展开后保持合理焦点顺序；不依赖 hover。窄屏下先减少装饰和多列，再调整密度，不能缩小所有文字解决拥挤。
- 语言切换用语言自身名称，不用国旗代替语言；尽量跳同一路径的对应版本，缺少翻译时明确标注。不要因浏览器偏好强制重定向到用户未选择的语言。
- 每页设置准确 `lang`；页面标题、描述、OG 信息、canonical、hreflang 与内容语言一致，不能只翻译可见文案。
- 主 CTA 明确区分 App Store、直接下载、TestFlight、外部产品站、尚未发布。不要把不可用产品做成无解释的 disabled 下载按钮。
- 产品归档时说明维护状态，保留必要支持与隐私内容；不能仅从首页隐藏使旧链接失效。
- 筛选若未来出现，默认显示全部；结果计数、空结果与重置入口完整。分享链接与返回操作应保留筛选状态。六款产品阶段可先不呈现筛选器。
- 不制造无实际用途的 cookie 横幅、注册表单或订阅入口。若只有邮件支持，直接提供明确联系动作和问题所需信息提示。

## 9. 无障碍与交互约束

### 已核对的标准事实

| 来源要求 | 应落入设计的约束 |
| --- | --- |
| WCAG 2.2 1.4.3：普通文字 4.5:1，大字 3:1，有定义与例外 | 辅助文字、产品强调色文字、按钮和浅色背景组合逐一校验 |
| 1.4.4：文字可放大至 200% 而不丢内容/功能；1.4.10：通常在 320 CSS px 等效宽度重排 | 禁止以固定高度截断正文；手机菜单、卡片、表格和语言入口都验证缩放 |
| 1.4.11：必要的非文字 UI 状态/图形与相邻色至少 3:1 | 焦点、选中状态和关键控件边界不能只靠很淡的灰线 |
| 2.5.8：目标最小 24×24 CSS px，有间距、行内等例外 | 设计值建议主要触控区域 44×44px 或更大；44px 是项目建议，不误称 AA 的统一门槛 |

规范原文：[WCAG 2.2](https://www.w3.org/TR/WCAG22/)。本表是相关条目的摘要，不构成完整合规结论。

2.4.11 要求获取焦点的组件不被作者内容完全遮住；本项目应以更好的可见性为目标，避免吸顶导航、底部 CTA 遮挡焦点和锚点。[焦点不被遮挡](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)

1.4.12 要求用户覆盖特定文字间距后内容与功能不丢失，不要求作者默认直接使用那些数值。验收应检查行高、段距、字距及词距改变后按钮和卡片仍完整。[文字间距](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)

MDN 说明 `prefers-reduced-motion` 用于检测用户的减少非必要运动偏好，大尺度平移/缩放可能引发不适。**本项目建议**减少动态效果时关闭视差、自动漂浮、滚动缩放与大位移出现效果，保留状态变化所需的即时反馈。[MDN reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)

### 本项目交互基线

- 内容不依赖滚动动画才出现；JavaScript 不可用时主体、导航与外链仍能工作。
- Hover、focus-visible、active、expanded、selected 各有明确样式；不会因鼠标离开导致已打开的必要信息消失。
- FAQ 优先原生 disclosure；图片放大若使用 dialog，支持 Esc、清晰关闭、焦点管理与恢复。
- 装饰图空 alt；产品截图用简短说明关键操作/结果的替代文字，不把屏幕上每个字全部抄进 alt。
- 链接与按钮语义一致；整张卡片可点击时不嵌套多个冲突点击区域。外链、下载、应用商店的名称清楚。
- 不默认自动播放有声视频；持续运动需可停止，关键功能说明不能只放在视频中。

## 10. 验证计划与设计完成标准

这些是建议的验收范围，尚未执行本项目实现检查。

1. **内容覆盖**：每个非 iCube 路径都有页面类型、语言、产品归属、素材状态与迁移策略；确认全部现有链接仍有效。
2. **模板覆盖**：至少预览首页、轻量工具产品、跨设备产品、支持、隐私、更新与 404；不能只证明首页漂亮。
3. **尺寸与语言**：320、390、768、1024、1440px，至少中/英/日；检查长标题、长平台串、不同语言按钮、缺失翻译、无截图和归档产品。
4. **状态**：键盘焦点、移动菜单、FAQ 展开、图片放大/关闭、目标锚点、系统减少动态效果、无 JavaScript、图片加载失败、200% 文字缩放。
5. **视觉**：截图不失真，窗口/设备尺寸有层级，文字不截断，辅助信息仍可读，颜色对比经计算，页脚不会因内容少而漂浮在不合理位置。
6. **性能**：代表性页面测首屏加载与布局稳定性，区分实验室结果和真实访问数据；不把一次 Lighthouse 分数称为全站持续性能。建议不因重设计引入运行时 UI 框架或大动画依赖。
7. **可维护性**：新增一个虚拟产品进行模板演练时，只需增加内容与素材，而不用复制整份 HTML/CSS；演练内容不得出现在生产发布目录。
8. **范围保护**：最终变更清单验证 iCube 源码、页面与依赖资产没有被直接或间接修改。

## 11. 仍待本项目实证回答的问题

- 首页主要访问来自已知产品用户、搜索发现还是开发者个人介绍？没有分析数据前，采用两者兼顾的目录结构，不声称某一类用户占多数。
- 哪些产品的真实截图已达到当前版本？缺失截图需要补齐或明确临时表达，不用视觉方案掩盖证据缺口。
- 六款产品是否有不同的维护/发布状态？状态必须以当前仓库或权威分发页核对。
- 现有多语言是否覆盖所有页面类型，还是只覆盖营销主页？语言路由设计必须照顾不完整情况。
- 现有静态模板能复用到什么程度？先审计当前生成链，再决定渐进提取共享模板的范围，避免为了设计重构整套发布流程。

这些不确定性不妨碍先完成视觉稿、token 与模板设计，但必须在生产迁移前得到明确处理。
